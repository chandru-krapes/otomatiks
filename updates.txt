# Ticket Management System — Technical Report

## 1. Executive Summary

1. **Where implemented**: Ticket management is split across two Django apps: **`apps/tickets`** (ticket *type* definitions, pricing, capacity, access, promo codes) and **`apps/registration`** (ticket *instances* are issued as part of a `Registration`/booking).
2. **Owning app**: `apps/tickets` owns the sellable "ticket product." `apps/registration` owns the act of acquiring one.
3. **Models involved**: `TicketType`, `TicketAccess`, `PromoCode`, `EventSubUnit` (all in `apps/tickets/models.py`); `Ticket` (also in `apps/tickets/models.py`, but represents an *issued* ticket, not a ticket type); `Registration`, `Attendee` (in `apps/registration/models.py`); `Payment` (in `apps/payments/models.py`) is the downstream consumer.
4. **APIs involved**: `apps/tickets/urls.py`, `apps/registration/urls.py`, and `apps/payments/urls.py` (for checkout). All mounted under `/api/v1/` (see `config/urls.py`).
5. **Ticket ↔ Event association**: `TicketType.event` is a required `ForeignKey` to `Event` (`on_delete=CASCADE`). All ticket-type endpoints are nested under `/events/<event_id>/...`.
6. **Frontend retrieval**: **Not found / cannot be confirmed from the current implementation.** There is no frontend code in this repository (this repo is `event_management_backend` only; per `AGENTS.md`, the public website is a separate Next.js application not present here, and no admin/dashboard frontend source exists in this repo either).
7. **Frontend updates**: Same as above — not present in this repository.
8. **Is ticket CRUD fully implemented?** No — **Create and Update exist; single-object Read does not** for `TicketType` (see §9/§10 below — `TicketTypeDetailView` has no `GET` handler). Delete exists as a **hard delete**, not a soft delete.
9. **Missing functionality** (see full list in §26): no `GET` single-ticket-type endpoint; ticket-type list is unpaginated with no search/sort; `GenerateEmptyTicketsView` is an explicit `501` stub; promo codes are validated but never actually applied to a booking's price; `Payment` amount calculation recomputes live from `ticket_type.price` rather than using the `Registration.total_amount` snapshot.
10. **Architectural issues discovered**: two parallel "ticket acquisition" flows exist side by side — the legacy single-ticket `RegistrationCreateView` (`POST /events/<id>/registrations/`) and the newer multi-attendee `BookingCreateView` (`POST /events/<id>/bookings/`) — both create `Registration` + `Ticket` rows, and both are live/reachable simultaneously.

## 3. Ticket Data Model

### `TicketType` — `apps/tickets/models.py` (this is the "sellable ticket product" the spec calls "Ticket")

| Field | Django Type | Required | Default | DB Column | Purpose |
|---|---|---|---|---|---|
| id | `BigAutoField` (from `TimeStampedModel`) | auto | auto | `id` | PK |
| event | `ForeignKey(Event, on_delete=CASCADE, related_name="ticket_types")` | yes | — | `event_id` | Owning event |
| name | `CharField(max_length=100)` | yes | — | `name` | Ticket type name |
| price | `DecimalField(max_digits=10, decimal_places=2)` | yes | `0` | `price` | Base price, **Decimal** (no float) |
| is_sponsored | `BooleanField` | no | `False` | `is_sponsored` | Flags sponsored/free-for-group tickets |
| capacity | `PositiveIntegerField` | no | `None` | `capacity` | Nullable = unlimited |

Properties (not DB columns — computed, see §6): `is_sold_out`, `is_available`.

## 4. Ticket Relationships

```text
Event (apps.events.Event)
   │
   ├──< TicketType (apps.tickets.TicketType)        FK event, on_delete=CASCADE, related_name="ticket_types"
   │       │
   │       ├──< TicketAccess (apps.tickets.TicketAccess)   FK ticket_type, CASCADE, related_name="access_items"
   │       ├──< Ticket (apps.tickets.Ticket)                FK ticket_type, PROTECT, related_name="tickets"
   │       ├──< PromoCode.applicable_ticket_types (M2M)
   │       └──< EventSubUnit.ticket_types (M2M)
   │
   ├──< PromoCode (apps.tickets.PromoCode)            FK event, CASCADE, related_name="promo_codes"
   ├──< EventSubUnit (apps.tickets.EventSubUnit)        FK event, CASCADE, related_name="sub_units"
   └──< Registration (apps.registration.Registration)   FK event, CASCADE, related_name="registrations"
           │
           ├──< Attendee (apps.registration.Attendee)      FK booking→Registration, CASCADE, related_name="attendees"
           ├──< Ticket (apps.tickets.Ticket)                FK registration, CASCADE, related_name="tickets"
           │       └── Ticket.attendee → Attendee            FK, SET_NULL, related_name="ticket" (nullable)
           ├──< Payment (apps.payments.Payment)              FK registration, PROTECT, related_name="payments"
           └── Registration.user → User (accounts)           FK, SET_NULL, related_name="registrations"
```

- **Tickets ↔ Events**: via `TicketType.event` (direct FK).
- **Tickets ↔ Organizations**: not found — no org-level model in this codebase; access is scoped by `EventMembership` (per-user, per-event).
- **Tickets ↔ Users**: not direct — `Ticket` has no `user` FK. A ticket is reached via `Ticket.registration.user`.
- **Tickets ↔ Bookings/Orders/Registrations**: `Ticket.registration` FK, as above. There is no separate "Order" model — `Registration` is the order/booking.
- **Tickets ↔ Attendees**: `Ticket.attendee` FK (nullable — only populated by the newer booking flow).
- **Tickets ↔ Payments**: indirect only, through `Payment.registration` → `Registration.tickets`. `Payment` has no direct FK to `Ticket` or `TicketType`.
- **Tickets ↔ Categories**: not found.
- **Tickets ↔ Ticket Access**: `TicketAccess.ticket_type` FK, as above.

## 5. Ticket Business Logic

| Rule | File | Function/Property | Behavior | Used by |
|---|---|---|---|---|
| Sold-out check | `apps/tickets/models.py` | `TicketType.is_sold_out` (property) | `capacity is not None and sold_count >= capacity` | `TicketTypeSerializer`, `TicketType.is_available` |
| Availability check | `apps/tickets/models.py` | `TicketType.is_available` (property) | `False` if paused, sold out, or `now` outside `[sales_start, sales_end]`; else `True` | `TicketTypeSerializer` only — **not** re-checked at booking time (booking-time checks are separate, see next row) |
| Capacity + window enforcement at booking time | `apps/registration/services.py` | `create_booking()` | Locks `TicketType` row with `select_for_update()`; rejects if paused, before `sales_start`, after `sales_end`, or `sold_count + quantity > capacity`; raises `RegistrationClosed`/`CapacityExceeded` | `BookingCreateView` |
| Capacity enforcement, legacy flow | `apps/registration/services.py` | `create_registration()` | Same locking pattern, but for exactly 1 ticket, checks `sold_count >= capacity` (not quantity-aware since quantity is always 1) | `RegistrationCreateView`, `OnsiteRegistrationCreateView` |
| Quantity derivation | `apps/registration/services.py` | `create_booking()` | `quantity = len(attendees)` — never accepted from the request body | `BookingCreateView` |
| Price calculation (booking flow) | `apps/registration/services.py` | `create_booking()` | `unit_price = ticket_type.price`; `total_amount = unit_price * Decimal(quantity)` — `Decimal` throughout, no float, no division | `BookingCreateView` |
| Price calculation (payment/checkout) | `apps/payments/services.py` | `_registration_amount()` | **Recomputes live**: `sum(t.ticket_type.price for t in registration.tickets)` — does **not** read `Registration.total_amount` | `create_zohopay_order()` |
| Booking reference generation | `apps/registration/services.py` | `_generate_booking_reference()` | `f"{event.slug-derived-prefix}-{year}-{registration_id:06d}"`, server-side only | `create_booking()` |
| Promo code validation | `apps/tickets/services.py` | `validate_promo_code()` | Checks existence, validity window, usage cap, ticket-type applicability. Returns `discount_type`/`discount_value` only — **does not compute a discount amount** (explicit `# TODO` in source: "the checkout flow applies it to the real cart total") | `PromoCodeValidateView` |
| QR rendering | `apps/tickets/services.py` | `render_qr_png()` | Encodes `ticket.qr_token` (not the raw ID) into a PNG | `TicketQrImageView` |
| Status transitions on cancellation | `apps/registration/services.py` | `cancel_registration()` | Sets `Registration.status = CANCELLED`, all child `Ticket.status = CANCELLED`, decrements each ticket's `TicketType.sold_count` | `RegistrationCancelView` |
| Initial booking status | `apps/registration/services.py` | `create_registration()` / `create_booking()` | `CONFIRMED` if `price == 0`, else `PENDING_PAYMENT` | Both create flows |

No `clean()`, no model-level `save()` overrides, and no Django signals exist anywhere in `apps/tickets` or `apps/registration` (confirmed by search — `apps/tickets/tasks.py` and `apps/tickets/permissions.py` are both **empty files**).

## 8. GET Ticket APIs

### List ticket types for an event
```http
GET /api/v1/events/{event_id}/ticket-types/
```
- **Auth**: `permissions.AllowAny` on the view (`TicketTypeListCreateView.permission_classes`).
- **Query params**: **none supported**. `apps/tickets/views.py::TicketTypeListCreateView.get()` does `TicketType.objects.filter(event_id=event_id)` with no search/sort/status filtering, and returns the serialized list directly — **not wrapped in `ListAPIViewMixin` pagination** (unlike `RegistrationListView`/`PaymentListView`, which are paginated).
- **Response** (plain JSON array, not `{results: [...]}`):
```json
[
  {
    "id": 1,
    "event": 4,
    "name": "General Admission",
    "price": "1000.00",
    "is_sponsored": false,
    "capacity": 100,
    "sold_count": 12,
    "sales_start": "2026-01-01T00:00:00Z",
    "sales_end": "2026-03-01T00:00:00Z",
    "is_registration_paused": false,
    "is_sold_out": false,
    "is_available": true,
    "access": [
      {"id": 1, "kind": "food"},
      {"id": 2, "kind": "workshop"}
    ]
  }
]
```

### Get single ticket type
```text
Not found / cannot be confirmed — TicketTypeDetailView has no `get()` handler.
```
`GET /events/{event_id}/ticket-types/{id}/` will return **405 Method Not Allowed**. There is currently no way to fetch a single `TicketType` by ID; a frontend must fetch the list and filter client-side, or use the (staff-only) `TicketDetailView`, which returns an **issued Ticket instance**, not the ticket type/product.

### Get a single issued Ticket
```http
GET /api/v1/tickets/{id}/
```
- **Auth**: `IsEventOrganizerOrVolunteerOrAdmin` — staff only, not for a public "Ticket Details" purchase UI.
- **Response**: `TicketSerializer` shape — `id, registration, ticket_type, qr_token, is_empty_ticket, status, qr_purpose, created_at`.

```http
POST /api/v1/events/{event_id}/ticket-types/
Content-Type: application/json

```
**Auth/permission**: not declared on the class (`permission_classes = [AllowAny]`), but `post()` manually checks `IsEventOrganizerOrAdmin().has_permission(request, self)` and calls `self.permission_denied(request)` if it fails.

```json

  "name": "General Admission",
  "price": "1000.00",
  "is_sponsored": false,
  "capacity": 100,
  "sales_start": "2026-01-01T00:00:00Z",

}
```

| Field | Required | Type | Purpose |
|---|---|---|---|
| name | yes | string | — |
| price | no (defaults `0`) | decimal string | — |
| is_sponsored | no | bool | — |
| capacity | no | int or null | — |
| sales_start / sales_end | no | ISO datetime or null | — |
| is_registration_paused | no | bool | — |

## 10. PUT/PATCH — Update Ticket Type API

```text
PUT: not implemented.
PATCH: implemented.
```
```http
PATCH /api/v1/events/{event_id}/ticket-types/{id}/
Authorization: Bearer <JWT>   (IsEventOrganizerOrAdmin)
```

(Both `IsEventOrganizerOrAdmin`, no request body, return the updated `TicketTypeSerializer`.)

## 11. DELETE — Ticket API

```http
DELETE /api/v1/events/{event_id}/ticket-types/{id}/
```
`TicketTypeDetailView.delete()` calls `ticket_type.delete()` — **this is a real, hard database delete**, not a soft-delete/`is_active` flag. There is no `is_active`/`archived`/`deactivated` field on `TicketType` at all. `Meta.on_delete` on `Ticket.ticket_type` is `PROTECT` — so deleting a `TicketType` that has any issued `Ticket` rows against it will raise `ProtectedError` at the DB layer (not caught/translated to a friendly API error anywhere in the view).

For issued `Ticket` instances: **no delete endpoint exists at all** — cancellation is done indirectly via `POST /registrations/{pk}/cancel/`, which sets `Ticket.status = "cancelled"` (a status change, not a delete).

## 12. Ticket Pricing

1. Base price field: `TicketType.price`.
2. `DecimalField(max_digits=10, decimal_places=2)` — confirmed `Decimal`, no floats anywhere in the pricing code path.
3. Backend calculates totals: **yes**, in `create_booking()` (`apps/registration/services.py`) — `total_amount = unit_price * Decimal(quantity)`. No division anywhere.
4. Pricing formula confirmed: **`base_price × attendee_count`** exactly, via `create_booking()`.
5. `unit_price`/`total_amount` are stored on `Registration` as a **snapshot at booking time** — later changes to `TicketType.price` do not retroactively change an existing booking's stored amount.
6. **Gap**: `apps/payments/services.py::_registration_amount()` (used by `create_zohopay_order`) recomputes the amount live from `sum(ticket.ticket_type.price for ticket in registration.tickets)` rather than reading `Registration.total_amount`. If `TicketType.price` changes between booking creation and payment/checkout, the payment amount will differ from the stored booking snapshot. This is an existing inconsistency in the code, not something introduced or fixed here.
7. Discounts: `PromoCode` exists and is validated (`PromoCodeValidateView`), but `validate_promo_code()` explicitly does not compute a discount amount (source comment: "Left as a TODO for the payments module build"), and `create_booking()` does not accept or apply a promo code at all.
8. Taxes: not found anywhere in the codebase.
9. Additional charges: not found.
10. Currency: `Payment.currency` (`CharField`, default `"INR"`) exists on `Payment`. `Registration`/`TicketType` have **no** currency field — `BookingSerializer.currency` is a hard-coded `"INR"` string in the serializer, not read from any model field.

## 13. Ticket Capacity

- **Capacity field**: `TicketType.capacity` (nullable = unlimited), **ticket-type level**, not event-level or booking-level.
- **Available capacity**: not a stored field — derived as `capacity - sold_count` implicitly via the `is_sold_out` property and the capacity check in `create_booking`/`create_registration`.
- `sold_count` is incremented directly at booking creation (by `quantity`) — it does **not** distinguish reserved/pending/confirmed/cancelled at the counting level; it is decremented back on cancellation (`cancel_registration`, per ticket, `-1` each). There is no separate reservation/hold state — a `pending_payment` registration already counts fully against capacity the moment it's created.
- **Overbooking prevention**: `TicketType.objects.select_for_update()` locks the row inside `transaction.atomic()` in both `create_registration` and `create_booking`, so two concurrent requests against the same ticket type serialize on that row — confirmed race-safe for concurrent bookings against the same `TicketType`.

## 14. Ticket Availability

- **Sales window**: `TicketType.sales_start` / `sales_end` (both nullable).
- **Active/paused**: `TicketType.is_registration_paused` (boolean).
- **Published status**: not applicable at ticket-type level (only `Event.status` has draft/published/cancelled — ticket types have no independent publish state).
- **Computed availability**: `TicketType.is_available` property — `False` if paused, sold out, or `now` outside the sales window; else `True`. Exposed in `TicketTypeSerializer` as `is_available` (boolean).
- **What the frontend should use for the "Buy" button**: the `is_available` field from the ticket-type list response. Note this field is only computed at serialization time (request time) — there's no cached/precomputed availability, so it reflects the live check.

## 15. Ticket Access

**CURRENT IMPLEMENTATION**: `TicketAccess` is a **separate normalized model** (not booleans, not a JSONField, not hard-coded strings) — `apps/tickets/models.py`. `kind` is a `TextChoices` field (`food`/`workshop`/`others`), FK'd to `TicketType`, `unique_together=("ticket_type","kind")`.

```text
TicketType
   └──< TicketAccess (FK ticket_type, CASCADE)
           kind: food | workshop | others
```

Exposed read-only, nested, in `TicketTypeSerializer.access` (`source="access_items"`, via `TicketAccessSerializer`). Response shape: `"access": [{"id": 1, "kind": "food"}, ...]`.

**GAP**: There is **no API endpoint to create, update, or delete `TicketAccess` rows**. It only appears as read-only nested output on the ticket-type list/create response. The only way to manage which access kinds a ticket type grants is through Django Admin (`TicketAccessInline` on `TicketTypeAdmin`) — not through any REST endpoint.

## 21. Error Responses

No custom exception handler is configured (`DEFAULT_EXCEPTION_HANDLER` not set in `REST_FRAMEWORK` settings) — standard DRF defaults apply:

- `400` — DRF's default `{field: ["error message"]}` shape for serializer validation errors. The booking flow additionally raises structured `{"detail": "...", "code": "registration_unavailable"}` for `CapacityExceeded`/`RegistrationClosed` (via `raise ValidationError({...})` in `BookingCreateView`), and `{"attendees": [{"field": ["This field is required."]}]}` for relationship-conditional attendee validation.
- `401` — DRF default `NotAuthenticated` when no credentials are supplied on an `IsAuthenticated`-protected view.
- `403` — DRF default `PermissionDenied`; also explicitly raised in `BookingDetailView` (`raise PermissionDenied()`) when an authenticated user isn't the booking's owner/staff.
- `404` — `get_object_or_404` used throughout for detail views; `BookingCreateView` also explicitly raises `NotFound({"detail": "Ticket not found.", "code": "ticket_not_found"})` for an unknown `ticket_id`.
- `409` — **not found / cannot be confirmed** — no view returns `409` anywhere in `apps/tickets` or `apps/registration`. Capacity conflicts currently return `400`, not `409`.
- `500` — unhandled exceptions (e.g. `Event.DoesNotExist` when an invalid `event_id` is passed to most of these views) propagate as unhandled `Http404`-unrelated exceptions and fall through to Django's default error handling; no custom stack-trace suppression beyond `DEBUG` setting.

```text
        ↓

        ↓

        ↓

        ↓
BookingCreateSerializer validates (relationship-conditional attendee fields)
        ↓
services.create_booking()  [transaction.atomic + select_for_update on TicketType]
    - quantity = len(attendees)

        ↓

    [idempotent via WebhookEvent; actual payload parsing/status update is a TODO stub]
```

```text
                    currency, attendees[])

```


```text
API endpoint:    GET /api/v1/events/{event_id}/ticket-types/
Field:           is_available (boolean, computed server-side per request)
```

### To display pricing

```text
                    creation time (POST .../bookings/), returned as "total_amount" in the

                    replicate `price × attendee_count` client-side for UX only — the
```
